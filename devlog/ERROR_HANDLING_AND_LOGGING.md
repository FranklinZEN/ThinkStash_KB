# Error Handling and Logging Guide\n\nThis document outlines the error handling and logging strategy for the Knowledge Card (KC) application backend.\n\n## 1. Logging Strategy\n\n### 1.1. Log Destinations\n\n*   **Cloud Logging (GCP):** All standard output (`stdout`) and standard error (`stderr`) from the deployed Cloud Run service (`kc-nextjs-backend-service`) are automatically captured by Google Cloud Logging. This is the primary destination for server-side application logs and errors.\n    *   Access: GCP Console -> Logging -> Logs Explorer. Filter by `resource.type=\"cloud_run_revision\"` and `resource.labels.service_name=\"kc-nextjs-backend-service\"`.\n*   **Google Cloud Error Reporting (GCP):**\n    *   Intended for aggregated and reported application errors. The Error Reporting API must be enabled for the project (`thinkstash-knowledge-base`).\n    *   Errors explicitly caught and reported (e.g., via a future `reportError` utility) or some unhandled exceptions should appear here.\n    *   Access: GCP Console -> Error Reporting.\n\n### 1.2. Log Content\n\n*   Application logs primarily use `console.log()` for informational messages (sent to `stdout`) and `console.error()` for errors or warnings (sent to `stderr`).\n*   Structured logging (JSON) is not currently implemented but may be considered for future enhancements for easier querying.\n\n## 2. Key Log Messages & Error Indicators\n\nThis section highlights critical log messages and what they indicate.\n\n### 2.1. Database (Prisma & Cloud SQL)\n\n*   **File:** `src/lib/prisma.ts`\n    *   **Log:** `CRITICAL: LIB/PRISMA.TS - Missing one or more environment variables for DATABASE_URL construction (DB_USER, DB_PASSWORD, DB_NAME, DB_HOST_PATH). Prisma will likely fail to initialize. Check Cloud Run secret configuration.`\n        *   **Indicates:** The runtime environment variables `DB_USER`, `DB_PASSWORD`, `DB_NAME`, or `DB_HOST_PATH` (sourced from secrets) are missing or not accessible to the Cloud Run instance. Prisma cannot construct its `DATABASE_URL`.\n        *   **Action:** Verify Cloud Run service configuration: \"Variables & Secrets\" tab must correctly map these environment variables to the corresponding secrets in Secret Manager. Ensure the Cloud Run service account has `Secret Manager Secret Accessor` IAM role.\n    *   **Log:** `LIB/PRISMA.TS: Initializing Prisma Client...`\n        *   **Indicates:** Prisma client initialization is about to be attempted.\n    *   **Log:** `LIB/PRISMA.TS: Prisma Client initialized.`\n        *   **Indicates:** Prisma client has been successfully initialized (or at least the constructor has run).\n    *   **Error (from Prisma, in `stdout` or `stderr`):** `error: Environment variable not found: DATABASE_URL.` (This should now be resolved by `lib/prisma.ts` constructing the URL).\n        *   **Indicates (Historically):** Prisma could not find the `DATABASE_URL` in `process.env` when its schema `url = env(\"DATABASE_URL\")` was processed.\n    *   **Error (from Prisma, in `stdout` or `stderr`):** `Can't reach database server at '/cloudsql/PROJECT:REGION:INSTANCE:5432'` (or similar path).\n        *   **Indicates:** Prisma has a `DATABASE_URL` but cannot connect to the Cloud SQL instance via the Cloud SQL Auth Proxy socket.\n        *   **Action:** \n            1.  Verify the Cloud SQL instance connection is **enabled** in the Cloud Run service revision's \"Connections\" tab.\n            2.  Verify the Cloud Run service account has the `Cloud SQL Client` IAM role.\n            3.  Check if the Cloud SQL instance itself is running and healthy.\n\n### 2.2. Authentication (NextAuth.js)\n\n*   **File:** (Typically in NextAuth event handlers or API routes using NextAuth)\n    *   **Error Log:** `[next-auth][error][NO_SECRET]` or `Error [MissingSecretError]: Please define a \`secret\` in production.`\n        *   **Indicates:** The `NEXTAUTH_SECRET` environment variable is not set for the NextAuth.js configuration in a production environment.\n        *   **Action:** Ensure `NEXTAUTH_SECRET` is set as an environment variable in Cloud Run, sourced from a secret in Secret Manager. Add `secret: process.env.NEXTAUTH_SECRET` to the `NextAuthOptions` / `authOptions`.\n    *   **Log (Example from `src/lib/auth.ts` if added):** `NEXTAUTH_ERROR_EVENT: [error details]`\n        *   **Indicates:** An error was caught by the NextAuth.js global error event handler.\n\n### 2.3. API Routes (General)\n\n*   **Example File:** `src/app/api/auth/signup/route.ts` (and other API routes)\n    *   **Log:** `Signup Error: [message]` (or similar for other routes, e.g., `Failed to fetch folders: [message]`)\n        *   **Indicates:** An error was caught in the `try...catch` block of the API route.\n        *   **Action:** Examine the error message and any associated stack trace (if logged) to understand the cause. This could be a validation error, an issue with business logic, or a failure from an underlying service like Prisma.\n\n## 3. Error Handling Philosophy\n\n*   **Server-Side:** All significant server-side errors in API routes or library functions should be caught and logged to `stderr` using `console.error()`, including the error message and stack trace where appropriate.\n*   **Client Responses:** API routes should return appropriate HTTP status codes (e.g., 400 for bad input, 401 for auth issues, 500 for server errors). Detailed error messages or stack traces should **not** be sent to the client in production responses; use generic error messages like \"Internal Server Error.\"\n\n## 4. Adding New Logging or Error Reports\n\n*   When adding new features, ensure that potential failure points in API routes or critical backend logic are wrapped in `try...catch` blocks.\n*   Log meaningful error information to `console.error()` within these `catch` blocks.\n*   For critical or unexpected errors that should be tracked more closely, consider integrating a call to an error reporting service (once a utility like `reportError` is established and tested).\n\n## 5. Review and Update\n\nThis document should be reviewed and updated as the application evolves, new error patterns emerge, or logging strategies change.

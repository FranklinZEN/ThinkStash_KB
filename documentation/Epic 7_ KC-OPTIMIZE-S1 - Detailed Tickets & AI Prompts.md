Focus on core CRUD operations for cards, folders, and tags first.

     * Long-running loops.  
     * Complex synchronous data transformations or calculations.

  3. **Implement Optimizations:** Refactor the problematic sections of code to improve efficiency. This might involve:  
     * Breaking down large synchronous tasks.

  4. **Verify and Document:** After applying optimizations, re-measure the response times of the modified routes to confirm they meet the target of \< 500ms (p95). Document the specific changes made and the performance improvement achieved for each optimized route."

### Ticket ID: KC-OPTIMIZE-DB-1

Title: Analyze and Optimize Slow Database Queries (Prisma & PostgreSQL \- Stage 1 Codebase)  
Epic: Epic 7: KC-OPTIMIZE-S1  
PRD Requirement(s): NFR-PERF-1, NFR-PERF-2  
TDD Reference(s): TDD v1.2, Section 1.A (Action B.1, B.2, B.3, B.4)  
Team: BE  
Dependencies (Functional): KC-OPTIMIZE-BE-1 (findings from API profiling can guide this)  
Dependencies (Technical): Local PostgreSQL database setup with Stage 1 schema and data. Prisma Client configured.  
Description (Functional): Identify and optimize slow database queries generated by Prisma in the Stage 1 application. This includes enabling query logging, analyzing query plans, optimizing Prisma query structures, and ensuring proper database indexing.  
Acceptance Criteria (Functional):

* Prisma query logging is enabled and logs are reviewed for slow queries associated with slow API routes.  
* EXPLAIN ANALYZE is used on identified slow SQL queries to understand their execution plans.  
* N+1 query problems are identified and refactored (e.g., using Prisma include or batched queries).  
* Data fetching is optimized to retrieve only necessary fields using Prisma select.  
* Missing database indexes on frequently queried columns (e.g., foreign keys, columns in WHERE or ORDER BY clauses) are identified and added via Prisma migrations.  
* Post-optimization, the performance of previously slow queries is demonstrably improved.  
  Technical Approach / Implementation Notes (for AI Vibe Coder):  
* **Prompt for AI Coder:** "Your task is to optimize slow database queries in the Stage 1 Next.js application using Prisma and PostgreSQL.  
  1. **Enable Query Logging:** Modify the Prisma Client instantiation (typically in src/lib/prisma.ts or similar) to enable query logging: const prisma \= new PrismaClient({ log: \['query', 'info', 'warn', 'error'\] });.  
  2. **Identify Slow SQL Queries:** Review the application logs (console output where Prisma queries are logged) when executing API routes identified as slow by KC-OPTIMIZE-BE-1. Capture the exact SQL queries that appear to be taking significant time.  
  3. **Analyze Query Plans:** For each slow SQL query, connect to the local PostgreSQL database (using psql or a GUI tool like pgAdmin) and run EXPLAIN ANALYZE \<your\_slow\_sql\_query\_here\>;. Analyze the output to identify bottlenecks like full table scans or inefficient joins.  
  4. **Optimize Prisma Queries:**  
     * **Refactor N+1 Problems:** Review the application code (API routes, service functions) where Prisma is used. Look for patterns where database queries are made inside loops (e.g., fetching a list of cards, then looping to fetch tags for each card). Refactor these to use Prisma's include option for eager loading related data in a single query, or implement batch fetching logic if include is not suitable.  
     * **Use select for Specific Fields:** Ensure Prisma queries only fetch the data fields actually needed by the application logic, using the select option to avoid over-fetching.  
  5. **Add Database Indexes:** Based on the EXPLAIN ANALYZE output and your review of WHERE clauses and ORDER BY clauses in common queries, identify columns that would benefit from indexing. Add these indexes to your prisma/schema.prisma file using the @@index(\[field1, field2\]) syntax within the relevant models. For example, if cards are often queried by userId and sorted by createdAt, you might add @@index(\[userId, createdAt\]) to the Card model.  
  6. **Apply Migrations:** After modifying schema.prisma, run npx prisma migrate dev \--name optimize-db-queries to generate and apply the database migration.  
  7. **Verify and Document:** Re-test the API routes and, if possible, re-analyze the optimized SQL queries to confirm performance improvements. Document the changes made (Prisma query refactoring, new indexes) and their impact."

### Ticket ID: KC-OPTIMIZE-FE-1

Title: Profile and Optimize Frontend Rendering Performance (Next.js/React \- Stage 1 Codebase)  
Epic: Epic 7: KC-OPTIMIZE-S1  
PRD Requirement(s): NFR-PERF-5, NFR-PERF-6  
TDD Reference(s): TDD v1.2, Section 1.A (Action C.1, C.2, C.3, C.4, C.6, C.7)  
Team: FE  
Dependencies (Functional): None  
Dependencies (Technical): Local Stage 1 frontend codebase. React Developer Tools.  
Description (Functional): Identify and optimize frontend performance bottlenecks in the Stage 1 Next.js/React application. This includes profiling component rendering, optimizing component structure and state management, reviewing data fetching, and ensuring efficient use of Chakra UI.  
Acceptance Criteria (Functional):

* React Developer Tools Profiler is used to identify slow-rendering components and unnecessary re-renders on key pages.  
* React.memo, useCallback, and useMemo are applied appropriately to optimize identified components.  
* List rendering is reviewed; if very long lists are present and cause slowness, virtualization is considered/implemented.  
* Zustand store selectors are reviewed for specificity to prevent unnecessary component re-renders.  
* Client-side data fetching logic is reviewed for efficiency (minimize data, handle loading states).  
* Chakra UI usage is reviewed for any overly complex style props on frequently updated components.  
* Target LCP for core pages is \< 2.5 seconds and INP \< 200ms locally after optimizations.  
  Technical Approach / Implementation Notes (for AI Vibe Coder):  
* **Prompt for AI Coder:** "Your task is to profile and optimize the frontend rendering performance of the Stage 1 Next.js/React application.  
  1. **Profile Components:** Using the 'Profiler' tab in React Developer Tools, record interactions with key pages (e.g., Dashboard, Card View, pages displaying lists of cards/folders). Identify components that have long render times (visible in the flamegraph) or are re-rendering unnecessarily.  
  2. **Apply Memoization:**  
     * For functional components that re-render with the same props, wrap them in React.memo.  
     * Use useCallback to memoize callback functions that are passed as props to memoized child components or used in dependency arrays of hooks like useEffect.  
     * Use useMemo to memoize the results of expensive calculations or to memoize object/array props passed to child components.  
  3. **Optimize List Rendering:** If any pages render very long lists of items (e.g., hundreds of cards) and exhibit slowness, implement list virtualization using a library like react-window or react-virtualized. This involves rendering only the items currently visible in the viewport.  
  4. **Optimize Zustand State Selectors:** Review all components that subscribe to the Zustand store (useMyStore(state \=\> ...)). Ensure that selectors are specific and only select the minimal state needed by the component. If a component re-renders due to unrelated changes in the store, refine its selector or split the store.  
  5. **Review Client-Side Data Fetching:** Examine how data is fetched in useEffect hooks or other client-side mechanisms. Ensure that data fetching is efficient, only necessary data is requested, and loading/error states are handled gracefully without blocking the UI. Check dependency arrays of useEffect to prevent infinite loops or excessive refetching.  
  6. **Chakra UI Review:** For components that are frequently updated or part of large lists, check if there's an overuse of highly dynamic Chakra UI style props that might be computationally intensive. If a specific Chakra UI component is identified as a bottleneck, consider optimizing its style props or using the sx prop for more complex static styles, or even pre-compiled styles (CSS Modules) for critical performance paths.  
  7. **Verify and Document:** After optimizations, re-profile the application to confirm improvements in LCP (Largest Contentful Paint) and INP (Interaction to Next Paint). Aim for LCP \< 2.5s and INP \< 200ms on core pages locally. Document the optimizations applied and their impact."

### Ticket ID: KC-OPTIMIZE-BUNDLE-1

Title: Analyze and Optimize Next.js Application Bundle Size (Stage 1 Codebase)  
Epic: Epic 7: KC-OPTIMIZE-S1  
PRD Requirement(s): NFR-PERF-5  
TDD Reference(s): TDD v1.2, Section 1.A (Action C.5)  
Team: FE  
Dependencies (Functional): None  
Dependencies (Technical): Next.js build tooling. @next/bundle-analyzer.  
Description (Functional): Analyze the JavaScript bundle sizes for the Stage 1 Next.js application and implement optimizations to reduce them, improving initial load time and interactivity.  
Acceptance Criteria (Functional):

* @next/bundle-analyzer is used to generate a bundle analysis report.  
* Large dependencies are identified.  
* Opportunities for code-splitting (e.g., using next/dynamic for components not needed on initial load) are identified and implemented where appropriate.  
* Unused code or dependencies are removed.  
* A measurable reduction in the main bundle sizes for key pages is achieved.  
  Technical Approach / Implementation Notes (for AI Vibe Coder):  
* **Prompt for AI Coder:** "Your task is to analyze and optimize the JavaScript bundle size of the Stage 1 Next.js application.  
  1. **Setup Bundle Analyzer:** Install @next/bundle-analyzer as a dev dependency (npm install \--save-dev @next/bundle-analyzer). Configure next.config.js to use it:  
     const withBundleAnalyzer \= require('@next/bundle-analyzer')({  
       enabled: process.env.ANALYZE \=== 'true',  
     });  
     module.exports \= withBundleAnalyzer({ /\* your other next.js config \*/ });

  2. **Generate Report:** Run the build with the analyzer enabled: ANALYZE=true npm run build. This will generate HTML reports in the .next/analyze/ directory.  
  3. **Analyze Report:** Open client.html and server.html from the reports. Identify the largest modules and chunks contributing to the bundle size. Pay attention to third-party libraries and large custom components.  
  4. **Implement Code Splitting:** For components or libraries that are large and not required for the initial rendering of a page (e.g., modals, complex editors only used on specific interactions, libraries for specific views), implement dynamic imports using next/dynamic:  
     import dynamic from 'next/dynamic';  
     const MyHeavyComponent \= dynamic(() \=\> import('../components/MyHeavyComponent'), { ssr: false /\* if not needed on server \*/ });  
     // Then use \<MyHeavyComponent /\> where needed.

  5. **Identify and Remove Unused Dependencies:** Use a tool like depcheck (npx depcheck) to find dependencies listed in package.json that are not being used in the code. Carefully review and remove them.  
  6. **Tree Shaking Review:** Ensure your code is structured to allow for effective tree shaking (e.g., using ES6 module imports/exports). While Next.js and Webpack handle this largely automatically, avoid patterns that might hinder it (like overly broad imports from libraries if only a small part is needed, though this is less common with modern tooling).  
  7. **Verify and Document:** After optimizations, rebuild and re-analyze the bundle. Document the specific changes made (dynamic imports, removed dependencies) and the percentage reduction achieved in the main JavaScript bundle sizes for key application pages."
